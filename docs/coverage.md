## Findings

- **COV-1** *(kept fixed by its regression test)* - FIXED 2026-11-03 - casts TIMESTAMP_S/MS to TIMESTAMP before strftime. Was: DuckDB TIMESTAMP_S and TIMESTAMP_MS values outside 1677-09-22 .. 2262-04-11 make `normalize` raise `Could not convert Timestamp(US) to Timestamp(NS)`: `strftime` binds its TIMESTAMP_NS overload for these types, so year 1, 1000 or 9999 kills the whole diff. Loud, not a false match; `cast(c as timestamp)` first would render them.
- **COV-2** *(kept fixed by its regression test)* - FIXED 2026-11-03 - one rule: sub-microsecond digits are compared iff both sides hold them (`Column.sub_micro`, set by the engine), and truncated with a caveat otherwise. Was: DuckDB TIMESTAMP_NS renders the nanosecond digits of a value that has them (`...00.123456700`), while the rules (`parity.reference`), SQL Server datetime2(7) and Snowflake TIMESTAMP_NTZ(9) truncate to the microsecond (`...00.123456`). The same sub-microsecond instant held on DuckDB and on SQL Server or Snowflake is therefore reported as different - a false alarm, not a false match - and the per-engine check disagrees with the rules on every such value.
- **COV-3** *(kept fixed by its regression test)* - FIXED 2026-11-03 - the DuckDB sample reads dates and timestamps as DuckDB's own text. Was: DuckDB sample path: the driver returns DATE/TIMESTAMP `infinity` as 9999-12-31 (23:59:59.999999) and `-infinity` as 0001-01-01, so the independent sample check reduces +infinity and 9999-12-31 to the same token. `normalize` itself is right (`infinity`); the second opinion is blind to the difference and reports a false verification failure for any infinite value.
- **COV-4** *(kept fixed by its regression test)* - FIXED 2026-11-03 - the reference parses DuckDB's `(BC)` as well as PostgreSQL's ` BC`. Was: DuckDB sample path: a BC date or timestamp comes back from the driver as text in DuckDB's spelling, `0044-03-15 (BC)`, which `parity.reference` does not parse (it reads PostgreSQL's ` BC` suffix), so every BC value is left unchecked by the sample check.
- **COV-5** *(kept fixed by its regression test)* - FIXED 2026-11-03 - as COV-3: the text carries all nine digits, and the reference truncates. Was: DuckDB sample path: the driver rounds a TIMESTAMP_NS to the nearest microsecond where the rules truncate, so `1969-12-31 23:59:59.9999999` is read as `1970-01-01 00:00:00`: the sample check's raw value is not the stored value.
- **COV-6** *(kept fixed by its regression test)* - FIXED 2026-11-03 - Snowflake TIME renders `to_char(c, 'HH24:MI:SS.FF9')` without trailing zeros. Was: Snowflake TIME (UNKNOWN-mapped) renders through `cast(c as varchar)`, which follows TIME_OUTPUT_FORMAT - `HH24:MI:SS` by default - and drops the fractional seconds: 12:34:56.5 and 12:34:56.123456 render `12:34:56`, exactly as 12:34:56 does there and on PostgreSQL, DuckDB and BigQuery. A FALSE MATCH, Snowflake to Snowflake and Snowflake to any engine.

## UNKNOWN-mapped types (scale 6)

Native types the dialect maps to UNKNOWN have no comparison rule: each engine compares them through its own text cast (escaped). Nothing guarantees two engines agree, and - the false-match risk - nothing guarantees one engine renders two different values differently. The sample checks the second on the values loaded: *collisions* are pairs of distinct values that render to the same text.
